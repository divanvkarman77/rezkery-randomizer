# План отдельной версии «Rezka Suite»

Ниже исходный план, выбранный пользователем перед разработкой. Начата экспериментальная реализация: [состояние alpha, проверки и оставшиеся задачи](IMPLEMENTATION_STATUS.md). Критерии каждого этапа используются для дальнейшей проверки; полный план пока не объявляется завершённым.

## Принципы объединения

Одна модель коллекции, один исполнитель заданий, одна политика запросов и отдельные оболочки платформ. Разные исходные архивы используются как источники конкретных механизмов. Простая и расширенная формы интерфейса обращаются к одной базе; параметры режимов сохраняются отдельно.

Существующие четыре браузерные сборки и Android остаются целевыми платформами. Для Chrome 109/Windows 7 и Firefox 115 ESR создаются собственные manifest и адаптеры. Современные платформы могут иметь дополнительные удобства, но перенос файлов коллекции работает между всеми вариантами.

## Структура будущего проекта

```text
packages/core/          модель, ID, объединение, маршруты, правила рандома
packages/formats/       старые JSON/HTML, новый JSON и пакет с медиа
packages/catalog/       чистый разбор карточек, пагинации и метаданных
packages/jobs/          описание задания и переходы состояний
extension/common/      общий интерфейс библиотеки и сервисы
extension/adapters/    Chrome worker/offscreen, Firefox background, browser session
android/               нативные хранение, UI, сеанс WebView и исполнитель
offline-viewer/        автономный HTML без extension API
fixtures/              сохранённые страницы и случаи миграции без личных данных
```

Это предлагаемая структура, а не уже созданные компоненты. Android использует общий формат и проверяемые алгоритмы, а платформенные вызовы реализует собственным кодом. Chrome API не становятся частью мобильного приложения.

## Этап 1. Переносимая база

**Работа:** реализовать модель из [DATA_MODEL.md](DATA_MODEL.md), numeric ID и алиасы путей; разделить библиотеку, историю рандома и статус просмотра. Добавить импортёр текущего Randomizer, Library, Manager, Saver, Offline Advanced и Desktop FAV. Поддержать известные HTML-экспорты. Перед импортом показывать число новых фильмов, дублей, папок, связей и неполных записей.

**Android:** перенести текущую коллекцию из SharedPreferences в Room/SQLite, сохранить старые настройки режимов, год и историю. **Расширения:** перейти от единого массива к IndexedDB; одна сборка из общих исходников и небольших платформенных адаптеров.

**Готово, когда:**

- Одна карточка с двух зеркал и с изменённым slug после импорта имеет один ID; разные фильмы с одним названием не объединяются.
- После цепочки Android → Chrome → Firefox → Android сохраняются число фильмов, папок и связей, история, описания и личные поля.
- Полный каталог не становится историей выбранных карточек; импорт RANDOM и старой базы рандомайзера пополняет её по выбранной политике.
- Повторный импорт того же файла не изменяет итоговое число фильмов/связей и не стирает заметки.
- Некорректный или будущий формат не очищает текущие данные.

## Этап 2. Задания, запросы, пагинация

**Работа:** общий диспетчер чтения каталогов, закладок, описаний и постеров. Любая фоновая операция имеет ID, снимок параметров, область каталога, очередь и контрольную точку после страницы/записи. Длинные операции не живут только в popup или глобальной переменной worker.

Состояния: `queued → running → completed`, с переходами в `paused_user`, `waiting_challenge`, `waiting_retry`, `cancelled`, `failed`. Остановка сохраняет завершённые данные; повторный запуск не создаёт второго worker для одного задания.

### Политика запросов

- По умолчанию один сетевой запрос к сайту одновременно, пауза 2 секунды; задержка выбирается в настройках. Описания, постеры, пагинация и закладки учитываются одной очередью.
- Ограничитель координирует зеркала одного сеанса, чтобы смена домена не обнуляла лимит. Иные независимые приложения без отдельного канала связи всё равно не могут гарантированно разделять один лимит; интерфейс не обещает такой гарантии.
- Сбой сети получает ограниченные повторы с увеличивающейся паузой. `429` учитывает `Retry-After`. Подозрение на Cloudflare/Anubis переводит операцию в ожидание пользователя и отменяет оставшиеся запланированные обращения.
- Прохождение проверки выполняется на странице сайта. После пользовательского завершения — один осторожный запрос проверки и продолжение с контрольной точки. Принудительная неизменяемая блокировка на 15 минут не нужна.
- История результата и количество попыток видны в журнале. Пароли, cookies и токены не попадают в журнал.
- Автоматическое получение описаний/оригиналов и автоматическая синхронизация включаются отдельно: обычное открытие библиотеки не запускает полное сканирование.

### Пагинация

Область задаётся зеркалом, маршрутом, годом, типом и query-параметрами. Поддержать общий `/page/N/`, `/year/YYYY/`, `/films/best/foreign/YYYY/`, `/series/best/YYYY/`, `filter/genre` и обнаруженные ссылки пагинации. Ссылки других разделов не участвуют в подсчёте текущего.

Проверять последнюю страницу по сохранённым образцам сайта; учитывать текущую страницу, `href`, `rel=next`, data-атрибуты и параметры. Хранить количество, время определения и источник значения: точное, ручное или пока неизвестное. Никакого скрытого постоянного лимита 2530.

Из 1.0.37 взять отпечаток набора карточек и проверку фактического адреса навигации. Если вместо страницы N вернулась страница 1, сохранить причину и остановить задачу, а не размножать карточки. Ручное число страниц хранится отдельно для каждой области.

**Готово, когда:** закрытие popup, перезапуск worker и возобновление не теряют прогресс; общая очередь не превышает выбранную частоту; challenge останавливает новые запросы; HTML одной страницы под разными номерами распознаётся; будущий рост числа страниц определяется без изменения кода.

## Этап 3. Закладки всех папок

**Работа:** использовать модель Library `movie ↔ folder`, разобрать `/favorites/` и все страницы каждой выбранной папки. RANDOM и DESKTOP FAV показываются как понятные отдельные области. Сначала сравниваются remote numeric ID фильмов; добавляются только отсутствующие связи.

Направления задаются явно: импорт с сайта, выгрузка выбранных локальных папок или объединение. Выгрузка всей библиотеки в RANDOM не является побочным эффектом запуска синхронизации. Автосинхронизация — отдельная галочка с областью и последним результатом.

В браузере транспорт использует подходящий авторизованный сеанс настроенного зеркала и может открыть временную неактивную вкладку. Проверяются происхождение сообщений, допустимый URL и принадлежность созданных вкладок операции; активная пользовательская вкладка не перенаправляется для фонового сбора.

На Android используется собственная авторизация WebView, сохранение cookies через CookieManager и то же описание операций. Прямое чтение cookies установленного Chrome не закладывается как доступный механизм мобильного приложения. Экран входа должен нормально открывать клавиатуру и страницу проверки сайта.

На сайте по исследованным архивам подтверждены операции папок/закладок. Перенос заметок, личных оценок и локальных коллекций через API HDRezka не подтверждён. Такие данные синхронизируются файлом/Gist, а не выдаются за данные папки RANDOM.

**Готово, когда:** два последовательных запуска синхронизации идемпотентны; один фильм в трёх папках имеет одну запись и три связи; смена зеркала не создаёт копию папки или фильма; истёкший сеанс и проверка защиты видны пользователю; прогресс содержит папки, страницы, обработанные/новые/пропущенные/ошибки.

## Этап 4. Общий менеджер библиотеки

Взять функции Manager: просмотр карточек, поиск по названию/оригиналу, тип, год, страна, жанр, статус, каталог, коллекция, несколько сортировок; отдельные оценки источников и личная оценка; заметки, избранное, ручные каталоги, коллекции и метки.

Список читает ограниченный набор записей через индексы/курсоры. Постеры и длинные описания не загружаются для всей базы при смене фильтра. На Android — нативный список с ограниченным числом созданных элементов; на desktop — большой экран с порциями, popup остаётся панелью быстрых действий.

Сохраняются последний раздел, фильтры, режим, год и прокрутка. Открытие фильма не закрывает библиотеку. Удаление записи, удаление связи и очистка истории — самостоятельные действия с понятным результатом.

**Готово, когда:** согласованные наборы 10k/50k/100k синтетических метаданных проходят измерения времени и памяти на целевых платформах; выдача страницы не читает всю базу описаний; все личные поля переживают экспорт, импорт и синхронизацию. Производительность пока не обещается конкретной цифрой — её фиксируют эти измерения.

## Этап 5. Офлайн-постеры, описания и HTML

Взять постоянный кэш Library, поиск оригиналов и сохранение уже полученных описаний; POST quick_content с numeric ID считать изученным кандидатом протокола, а ответы зеркал отдельно подтвердить тестовыми страницами и ограниченной живой проверкой.

Медиа отделены от структурированных метаданных. Настроить объём кэша, статистику, очистку только медиа, получение пропущенных изображений/описаний и отмену операции.

Один автономный HTML-просмотрщик заменяет несколько почти одинаковых экспортёров: выбор списка/карточек, фильтры AND, тема, колонки, размер постера, увеличение и навигация, описание, рандом среди сохранённых фильмов, выбор домена открытия. Можно экспортировать всё, каталог или коллекцию. Для обновления старого HTML сопоставлять фильмы по ID и добавлять недостающие сведения.

Сайт передаёт данные, а интерфейс и CSS принадлежат приложению. Импортированные HTML-фрагменты очищаются по разрешённым элементам/атрибутам; скрипты импортируемого файла не выполняются. Это особенно важно при повторном импорте экспортов других приложений.

**Готово, когда:** режим с встроенными постерами и описаниями открывается без сети, повторный экспорт использует кэш, неполное обогащение не стирает данные, HTML работает в целевых браузерах и мобильном просмотре; чрезмерно большой экспорт предлагает полный пакет с медиа вместо зависания одного HTML.

## Этап 6. Синхронизация устройств и выпуск

Первыми реализуются JSON и ZIP с медиа, затем лёгкий Gist с метаданными, журналом изменений и явными удалениями. Облачные конфликты заметок/оценок сохраняются для разрешения. Отдельно можно добавить Google Drive OAuth/API; текущий системный выбор файла на Android не является этой функцией.

Каждый вариант проверяется в своей среде: Chrome 109/Windows 7, современный Chrome, Firefox 115 ESR, современный Firefox, Android. Проверки включают импорт всех семейств, соответствие модели, сообщения между процессами, закрытие popup, восстановление операций, пограничные годы, разные зеркала и ограничение запросов. На Android дополнительно — вход, клавиатура, поворот/пересоздание Activity, возврат к списку и сохранение файлов.

Сборка из общих исходников должна выдавать четыре ZIP; APK пересобирается при изменении Android. Ссылки на новые сборки выдаются после успешных проверок; запланированные функции не объявляются готовыми по одному лишь успешному синтаксическому анализу.

## Границы текущего этапа

Подготовлены разбор, модель и поэтапный план. Оригинальные архивы сохранены локально для дальнейшей разработки; в исследовательскую ветку входят документы и их контрольные данные. Исходники текущего Android и расширений этим этапом не меняются.
