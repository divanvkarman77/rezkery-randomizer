# Проект общей базы и переноса данных

Это спецификация будущего формата, а не уже реализованный импортёр. Все примеры ID ниже условные.

## 1. Три независимых состояния фильма

1. **Библиотека** — фильм известен приложению: импортирован, найден при сканировании или добавлен вручную.
2. **История подбора** — фильм был выбран рандомайзером или явно импортирован как уже выбранный. Используется для исключения повторов.
3. **Просмотр** — пользователь планирует смотреть, смотрит, закончил или отложил. Не выводится автоматически из факта открытия ссылки.

Сканирование каталога добавляет фильмы в библиотеку. Оно не пополняет историю подбора. Импорт старой базы рандомайзера переносит её `used` и выбранные `items` в историю. Папка RANDOM может пополнять историю согласно отдельной настройке; другие папки остаются обычными связями библиотеки.

При объединении выбранный фильм сохраняется до открытия внешней вкладки/приложения. Ошибка открытия отмечается отдельно: повторный импорт или возобновление задания не должны создавать второй фильм.

## 2. Единая идентичность

Приоритет ключей:

1. Проверенный числовой ID HDRezka из карточки, `data-id`, канонического ID старой базы или маршрута фильма: `rezka:12345`.
2. При отсутствии ID — нормализованный путь карточки: `path:/films/drama/example.html`. Удаляются домен, параметры, fragment и лишний конечный `/`; тип контента не включается в этот запасной ключ.
3. Запись без ID и пригодного адреса получает локальный UUID и попадает в список неполных записей.

Название и год дают подсказку о возможном дубле, но не служат основанием для автоматического слияния. Разные фильмы могут иметь одинаковые название и год.

Если позднее найден numeric ID для записи с ключом по пути, миграция в одной транзакции переносит все связи, историю, личное состояние и медиа. Старые ключи остаются алиасами. Старые резервные копии с путями должны находить тот же фильм после миграции.

Пример: `https://rezka.fi/films/drama/12345-example.html` и `https://rezkery.com/films/drama/12345-new-slug.html` соответствуют одному numeric ID даже после изменения slug. Разные numeric ID автоматически не объединяются.

Хранятся раздельно: `movieId`, известные исходные URL, предпочитаемое зеркало открытия, зеркало текущего авторизованного сеанса. Выбор нового зеркала не переписывает идентичность и пользовательские данные.

## 3. Сущности

| Сущность | Основные поля и назначение |
| --- | --- |
| `movies` | `id`, `rezkaId`, пути/URL, название и оригинальное название, фактический год, тип, страны/жанры, описание, режиссёр/актёры, рейтинги сайта/IMDb/КП, источники и время обновления |
| `aliases` | Старый ключ/путь → `movieId`, включая ключи предыдущего рандомайзера |
| `catalogs` | Раздел сайта, год, персона или ручная подборка; нормализованный источник и параметры запроса |
| `folders` | Локальные папки, в том числе RANDOM и DESKTOP FAV; локальный стабильный UUID |
| `memberships` | Фильм ↔ каталог/папка; связь уникальна по двум ID, отдельный порядок при необходимости |
| `remoteBindings` | Аккаунт и домен сеанса, local folder ID, remote folder ID, последняя успешная сверка |
| `userState` | `movieId`, статус просмотра, личная оценка, избранное, заметка, время изменения |
| `collections`, `collectionItems` | Пользовательские коллекции и их состав |
| `tags`, `movieTags` | Метки и связи; перенос имеющихся данных, затем пользовательский редактор |
| `randomHistory` | Уникальные события подбора/импорта RANDOM/исторической базы; ID события, фильм, время, источник |
| `assets` | Постеры и оригиналы, тип, размер, хеш, локальный файл/Blob и URL-источник |
| `jobs` | Сохраняемое задание, параметры, очередь, контрольная точка, попытки, состояние защиты и прогресс |
| `syncState`, `tombstones` | Состояние обмена и явные удаления для предотвращения восстановления удалённого при следующей сверке |

Год фильма берётся из метаданных карточки/страницы; год каталога и год запроса хранятся отдельно. Пустой фильтр года означает весь каталог. Текущий календарный год не используется как скрытое значение фильтра.

Сайт может предоставлять разные рейтинги и число голосов; личная оценка хранится отдельным полем и не заменяет рейтинг источника. Числа, даты и типы нормализуются при импорте, а не на каждом отображении списка.

## 4. Формат обмена

Предлагаемый заголовок лёгкой JSON-копии:

```json
{
  "format": "rezka-suite",
  "schemaVersion": 1,
  "exportedAt": "2026-10-21T00:00:00Z",
  "exportId": "example-export-uuid",
  "movies": [],
  "aliases": [],
  "catalogs": [],
  "folders": [],
  "memberships": [],
  "userState": [],
  "collections": [],
  "collectionItems": [],
  "tags": [],
  "movieTags": [],
  "randomHistory": [],
  "tombstones": [],
  "assetManifest": []
}
```

Лёгкий JSON содержит метаданные и ссылки на изображения. Полный переносимый пакет — ZIP с таким JSON, манифестом файлов и `assets/<hash>.<extension>`. При импорте проверяются версии, хеши, размеры и безопасные пути ZIP; неизвестные будущие версии не должны молча очищать базу.

Токены Gist/Drive, пароль и cookies не включаются в переносимую базу. Обновление устройств переносит коллекцию, а сеанс сайта каждое устройство поддерживает отдельно.

Gist получает лёгкую копию метаданных. Постерный кэш с десятками тысяч изображений не отправляется в Gist как один гигантский JSON. Полная резервная копия с медиа сохраняется файлом; отдельная автоматическая интеграция Drive рассматривается после устойчивого локального обмена.

Экспорт для старого рандомайзера остаётся отдельной командой: `format: "rezkery-randomizer-db"`, `version: 1`, `items`, `used`. Пользователь видит, что этот старый формат не передаёт весь набор коллекций и личных метаданных нового приложения.

## 5. Адаптеры старых форматов

| Источник | Определение | Преобразование |
| --- | --- | --- |
| Текущий Randomizer Android/расширения | `rezkery-randomizer-db`, версия 1; также старый массив | `items` → movies, `used` и исторические выбранные items → randomHistory; `date/addedAt` → нормализованные даты |
| Library 0.4.5 / Chrome 0.5.8 / Firefox 0.5.5 | `rezka-library`, `formatVersion`, `items/categories/memberships` | `contentKey/id` и URL → movie ID; отдельные папки и все memberships; descriptions и posterOriginal сохраняются |
| Desktop `favorites.json` | Массив или известная оболочка записей `id/title/url/entity_type` | Категория DESKTOP FAV, ID и данные карточек; не определять формат только по имени файла |
| Catalog Manager 5.2.17 | `format: RezkaCatalogManager`, версия 1 | `sourceHref/href` → URL/алиасы; movies плюс отдельные posters/descriptions/userState/collections/collectionItems/tags/movieTags; каталоги и все связи |
| Catalog Saver 4.5.4 | Старые `movies`, `catalogs` и раздельные части базы | Поддержать массивы и словари, встроенные details/poster, затем раздельные медиаданные; собрать связи каталогов |
| Offline Advanced 1.0.37 и 1.1.0 | `categories` с `baseUrl`, `cards`, `pages`, `styles` | category → catalog, cards → movies и memberships; `url`, а при необходимости `data-rk-source` из HTML; метаданные и описания отделяются от сырого HTML |
| Offline Simple 1.1.0 | Автономный HTML; отдельной команды JSON в popup нет | Разбор известной структуры HTML и data-rk-атрибутов; результат показывается до записи |
| HTML Randomizer/Library/Offline | Встроенные `rezkery-data`/`rezkery-db` либо известные карточки и категории | Сначала структурированные данные, затем безопасный разбор HTML без выполнения скриптов; сохранение обнаруженных папок и предупреждение о неполных полях |

Варианты оболочек и точные версии финализируются по сохранённым пользовательским копиям на этапе реализации. Присланные ZIP содержат код расширений, но не реальные JSON-копии пользователя; тестирование на реальных коллекциях ещё необходимо.

Невозможно читать IndexedDB другого установленного расширения напрямую как собственную базу. Основной путь переноса — его экспорт JSON/HTML, затем адаптер; при необходимости для старого исходного приложения готовится отдельный экспортёр.

## 6. Правила слияния

- ID и ссылки сопоставляются до переноса связей; доменные дубли не создают повторные события истории.
- Каталоги, папки, коллекции и метки объединяются как множества связей. У фильма сохраняются все его папки.
- Пустое описание или неудачный ответ не заменяют уже сохранённое описание. Кэш медиа повторно используется по фильму и хешу файла.
- Ручное исправление пользователя имеет приоритет перед новым сканированием. Источник значения и время изменения сохраняются.
- Конфликт личных заметок/оценок с двух устройств сохраняется для разбора; одно изменение не затирает другое без следа.
- Каталог с одинаковым URL, но разными `genre/filter/year`, остаётся отдельной областью сбора.
- Аккаунты HDRezka получают раздельные remote bindings. Одинаковое название папки не является подтверждением одного аккаунта.
- Удаление из локальной коллекции, исключение из истории и удаление закладки на сайте — разные действия. Сетевое удаление не выводится из отсутствия записи в одном неполном импорте.
- Восстановление пакета выполняется через проверенную промежуточную область и транзакцию. Ошибка в конце файла не должна оставлять половину миграции.

## 7. Хранение и индексы

Расширения: IndexedDB с отдельными хранилищами медиа и индексами по ID, названию, году, типу, времени изменения и связям. Запрос списка не читает все описания и изображения. `storage.local` хранит небольшие настройки и указатели состояния.

Android: Room/SQLite для структурированных сущностей; файлы постеров в отдельном каталоге приложения. Миграция текущего JSON в SharedPreferences выполняется один раз после контрольной резервной копии и проверки числа записей/связей. Данные настроек остаются небольшими и независимыми от объёма библиотеки.

Идентичность и наборы тестовых примеров одинаковы для браузерного и Android-кода. Проверки должны сравнивать одни и те же случаи: доменные алиасы, другой slug при прежнем numeric ID, неполные URL, неизвестный год, пустые поля и повторный импорт.
